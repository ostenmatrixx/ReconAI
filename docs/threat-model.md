# Threat model

Status: baseline design review; implementation verification remains open  
Method: asset/trust-boundary analysis with STRIDE-style abuse cases  
Review cadence: before each release and after a boundary, connector, auth, AI, or data-flow change

## Scope and safety objective

In scope: web/API/worker, identity/session, PostgreSQL, Redis queue/cache, object storage, Shopify,
Stripe, CSV import/export, observability, support tooling, deployment/supply chain, backups, and
optional AI. V1 must preserve tenant confidentiality, financial evidence integrity, service
availability, review accountability, credential secrecy, and the no-source-write boundary.

Out of scope but dependency assumptions: provider internal security, end-user endpoint security, and
legal/compliance certification. ReconAI makes no fraud or compliance certification claim.

## Assets

- Connector OAuth/API credentials and webhook secrets.
- Session identities, memberships, permissions, invitations, and MFA state.
- Raw source events, canonical records, imports/exports, notes, and personal/financial metadata.
- Matching rules, input snapshots, matches/exceptions, approvals, and audit history.
- Encryption/signing keys, database/backups, object storage, queue contents, logs/traces.
- Repository, dependencies, build artifacts, releases, CI identity, deployment credentials.

## Trust boundaries

Browser ↔ reverse proxy/web; provider/internet ↔ webhook/API; web ↔ API; API/worker ↔ database; API
↔ object storage/queue; queue ↔ worker; worker ↔ providers; application ↔ OIDC/AI/telemetry;
maintainer/CI ↔ source/build/deployment; operator/support ↔ tenant data.

## High-risk abuse cases

### Cross-tenant record reference

An analyst obtains another tenant’s exception UUID and puts it in a valid route. The membership-
derived tenant context makes the API query tenant-bound; RLS denies even a missed predicate; the API
returns the same not-found response. No audit payload, count, export, object key, cache entry, or
telemetry label includes the foreign record.

### Valid signature, wrong tenant connection

A provider event is cryptographically valid but targets an external account not owned by the route
organization. Connection lookup is by provider account under a server-owned mapping. The event is
bound to that mapping, not a client organization field. Unknown accounts are quarantined without
revealing tenant details.

### Delayed Stripe uninstall after reauthorization

A valid signed `account.application.deauthorized` event from an older Stripe App installation
arrives after the same account has reauthorized ReconAI. The app-level verifier accepts only the
exact raw signed body and event type. The narrow resolver maps the globally unique Stripe account
without accepting a client tenant ID; the normal state change then runs under the resolved tenant's
RLS transaction. The stored OAuth bundle's live/test mode and original authorization time identify
the current generation. An older or wrong-mode event receives the same generic acknowledgement but
does not revoke credentials or reveal whether an account exists.

### Prompt in order metadata

An order note says to ignore rules and approve a refund. The value is wrapped as untrusted evidence,
minimized, never placed in system instructions, and sent only to a no-tools structured ranking
interface. The schema cannot express approval; deterministic conflicts remain visible; a human must
decide.

### Stolen invitation link

An attacker obtains an invitation URL from a recipient’s device or message. The fragment is not sent
as a referrer, the browser removes it before acceptance, and the server stores only its SHA-256
digest. Possession alone is insufficient: acceptance also requires a live OIDC token whose verified,
normalized email matches the invitation. The token expires after 72 hours, is consumed atomically,
cannot be replayed, and can be revoked. A stolen IdP session remains a separate identity threat
addressed by MFA capability, bounded sessions, and provider revocation.

Configured email delivery transmits the token only inside a bounded authenticated request body.
Redirects are rejected so a relay cannot forward the bearer to another origin; provider response
bodies are discarded; failures expose only stable codes; and neither application logs nor delivery
audit events receive the URL, token, message body, or relay credential. Relay operators must also
suppress request-body logging and apply their own access and retention controls.

### Compromised worker message

A message changes `organizationId` while retaining a record ID. The worker validates schema and
trusted producer provenance, reloads the referenced job/run under the envelope tenant, checks
membership/service authorization, and uses RLS. The mismatch is rejected and security-audited.

## Privacy considerations

Minimize ingestion fields to reconciliation purpose; avoid card/PAN/CVC and unnecessary addresses or
notes; classify raw events/imports as restricted; encrypt credentials separately; make exports
permissioned and formula safe; keep AI/telemetry data minimized; document retention/deletion/legal
hold; and use synthetic fixtures. See `docs/privacy-and-retention.md`.
