## Requirement gap closed locally

The PRD requires an operator to edit a proposal. The prior implementation protected proposal
evidence from mutation but allowed a new version only after rejection or automatic supersession. It
therefore did not provide the promised edit action while a proposal was pending.

The implemented action is an immutable revision:

- only the authenticated original proposer may revise the tenant-scoped exception while exactly one
  proposal is pending;
- the transaction changes only the old proposal's lifecycle status to `superseded`, inserts a new
  UUID/version, recomputes required approvals from current organization policy, and appends
  `resolution.revised`;
- existing approval rows remain append-only and bound to the old proposal ID/version, so the
  replacement always begins with zero approvals;
- approval and revision acquire the exception authority row in the same order before locking the
  proposal, preventing a concurrent decision from crossing into the replacement;
- another review-capable actor cannot revise, and the BFF exposes only the server-derived
  `canRevise` decision rather than proposer identity;
- the operator must confirm that prior approvals remain historical before submitting a replacement.

No migration was required. Migration 0015 already permits `superseded`, rejects proposal-evidence
mutation, and makes approvals append-only and version-bound.
